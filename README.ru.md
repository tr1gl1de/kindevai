# kindevai — AI Development Platform

[English version](README.md)

Self-hosted платформа, которая превращает задачи YouTrack в изменения кода. Код пишут AI CLI (Codex, Claude Code,
ZCode) на внешних runners. Проект в активной разработке; спецификация находится в Knowledge Base YouTrack
(проект `KIN`, корневая статья `KIN-A-1`).

## Архитектура кратко

- **Control Plane** — один Go-процесс (модульный монолит), SQLite в режиме WAL, React Dashboard встроен через
  `go:embed`. Цель — VPS 1 vCPU / 1 GB RAM. Без PostgreSQL, Redis, Temporal и RabbitMQ.
- **Runner** — Go-демон для Linux/WSL2/macOS; подключается к Control Plane исходящим WSS и запускает AI CLI
  в изолированных git worktree.
- **Web UI** — React + TypeScript, работает и как Telegram Mini App.

## Структура репозитория

| Путь | Содержимое |
|---|---|
| `cmd/ai-platform` | Бинарник Control Plane (`serve`, `version`) |
| `cmd/ai-runner` | Демон раннера (`enroll`, `fingerprint`, `run`, `version`) |
| `internal/` | Go-пакеты Control Plane (`internal/runner/...` — раннер, `internal/protocol` — общие wire-сообщения) |
| `web/` | Dashboard на React + TypeScript (Vite); `web/embed.go` встраивает сборку |
| `scripts/` | Вспомогательные скрипты (worktree задач, учёт времени) |
| `.claude/` | Правила, агенты и skills Claude Code для разработки репозитория |

## Требования

Go (версия в `go.mod`), Node.js 24+ и npm (только для сборки web UI), `make`.

## Быстрый старт

```bash
make build            # собирает web/dist/app, затем bin/ai-platform со встроенным UI
./bin/ai-platform serve   # http://127.0.0.1:8080
```

`ai-platform serve --addr 127.0.0.1:9000` меняет адрес. Бинарник, собранный без web UI, тоже запускается
и показывает страницу-заглушку.

### Каталог данных и ключ шифрования

При первом запуске `serve` создаёт `./data` (флаг `--data-dir`), SQLite в режиме WAL (`data/db/platform.db`),
применяет миграции схемы и генерирует ключ шифрования `data/secrets/master.key` (права 0600; `--key-file` позволяет
хранить его в другом месте). Следующие запуски используют существующие данные. **Берегите ключ — без него резервная копия бесполезна (см. «Резервное копирование, восстановление и перенос»):**
если база есть, а ключа нет или он другой, Control Plane не запустится и никогда не создаст ключ взамен.
Каталог данных одновременно может использовать только один процесс.

### Первая настройка

Новая установка стартует в режиме setup. Для создания первого Owner нужен одноразовый **setup token**. Он никогда
не выводится в логи и не отдаётся по HTTP: он записывается в `data/secrets/setup-token` (права 0600; в логе только
путь). Прочитайте его на хосте (`ai-platform setup-token` или `docker compose exec cp ai-platform setup-token`)
и введите в мастере Dashboard вместе с логином Owner, паролем (от 12 символов) и названием платформы. Токен
действует час и обновляется автоматически; после настройки он удаляется, и повторить setup нельзя — в том числе
после рестарта.

### Вход

После настройки войдите с логином и паролем Owner. Сессии хранятся на сервере: браузер получает cookie HttpOnly,
SameSite=Strict (Secure при HTTPS); сессия завершается после 12 часов бездействия, не позже чем через 7 дней,
или при выходе. Все API, кроме health, setup, входа, принятия приглашения и регистрации раннера, требуют сессию; изменяющие запросы с чужого origin
отклоняются, попытки входа ограничены по адресу и по учётной записи.

### Проекты и доступ

Owner создаёт проекты и выдаёт участие (`project_admin` или `member`); в MVP участниками управляет только Owner.
Пользователь видит только свои проекты — любой другой отвечает `404`, так же как несуществующий. API:
`GET/POST /api/projects`, `GET /api/projects/{id}`, `GET /api/projects/{id}/members`,
`PUT/DELETE /api/projects/{id}/members/{login}`.

### Раннеры

Owner добавляет машину на странице **Раннеры**: **Добавить раннер** показывает одноразовый токен регистрации (256 бит,
действует 10 минут, хранится только SHA-256) и команду для этой машины — `ai-runner enroll --server <URL>`; токен она
запрашивает через stdin, поэтому он не попадает в argv и историю shell. Раннер создаёт пару ключей Ed25519 и регистрирует
открытый ключ через публичный `POST /api/runners/enroll` с ограничением частоты; раннер получает статус **ожидает
одобрения** и не может подключаться и получать работу. Owner сверяет отпечаток в стиле OpenSSH (`SHA256:…`, как у
`ssh-keygen -lf`) с выводом `ai-runner fingerprint` на машине и одобряет раннер для явного списка проектов; позже
можно менять проекты, отключать/включать и отзывать раннер (отзыв окончателен; повторная регистрация — с новым ключом).
Удалённым раннерам нужен HTTPS (профиль Caddy); обычный HTTP — только для раннера на том же хосте. API Owner:
`POST/GET /api/runners/enrollment-tokens`, `POST /api/runners/enrollment-tokens/{id}/revoke`, `GET /api/runners`,
`GET /api/runners/{id}`, `POST /api/runners/{id}/{approve|disable|enable|revoke}`, `PUT /api/runners/{id}/projects`.

### Демон раннера (`ai-runner`)

`ai-runner` — второй бинарник (`cmd/ai-runner`, linux/darwin × amd64/arm64, архивы релиза
`kindevai-runner_<версия>_<os>_<arch>.tar.gz`). Команды: `enroll`, `fingerprint`, `run`, `version`.

```bash
ai-runner enroll --server https://kindevai.example.com   # спросит токен без отображения ввода
ai-runner fingerprint                                    # сверьте с карточкой раннера перед одобрением
```

- Токен читается из скрытого prompt, из stdin (`… | ai-runner enroll --server …`) или из `--token-file <путь>`
  (файл с правами 0600); `--token` и позиционные аргументы отклоняются.
- Ключ Ed25519 создаётся один раз при первом `enroll` (`keys/ed25519.pem`, PKCS#8, права 0600) и никогда не
  заменяется: повреждённый ключ — ошибка, а ключ или конфиг, доступные другим пользователям, отклоняются (`chmod 600`).
  Повтор с тем же токеном после обрыва использует тот же ключ. Fingerprint, который вернул Control Plane, обязан
  совпасть с локальным ключом, иначе регистрация не сохраняется.
- Сертификаты TLS проверяются всегда; флага insecure нет. `http://` работает только для Control Plane на
  `localhost`/loopback, и соединение по http возможно только с loopback-адресом. Переменные прокси (`HTTPS_PROXY`) для канала управления игнорируются, редиректы не выполняются.
- Каталог данных (`--data-dir`): `/var/lib/kindevai-runner` под root, иначе `$XDG_DATA_HOME/kindevai-runner` или
  `~/.local/share/kindevai-runner`. В нём `config.json` (сервер, id раннера, fingerprint; 0600), `keys/` и
  `repos/ workspaces/ sessions/ events/ proxy/`, все с правами 0700; одновременно — только один процесс (lock-файл).
- Сервисы: `deploy/runner/kindevai-runner.service` (системный сервис systemd под отдельным пользователем),
  `kindevai-runner-user.service` (пользовательский сервис systemd, например в WSL2, чтобы AI CLI использовали ваши
  логины) и `io.kindevai.runner.plist` (агент launchd для macOS); шаги установки — в каждом файле.
- `ai-runner run` держит исходящий WebSocket к `wss://<сервер>/runner/connect` (`ws://` — только для Control Plane на
  loopback). Каждое подключение проходит challenge-response: Control Plane присылает одноразовый 32-байтный nonce,
  привязанный к id соединения и своему адресу, раннер подписывает
  `kindevai-runner-auth/1\n<id раннера>\n<audience>\n<nonce>\n<срок>\n<id соединения>` своим ключом Ed25519, и
  впускается только **одобренный** раннер (ожидающий/отключённый получает отказ и повторяет попытки, отозванный
  останавливает демон с кодом 78). Отключение или отзыв раннера сразу закрывает его активное соединение и в той же
  транзакции проваливает его идущие попытки (повтор на другом раннере); раннер сам останавливает их процессы, как только
  узнаёт об отключении или отзыве, не дожидаясь Control Plane (KIN-63). Раннер
  переподключается с экспоненциальной задержкой с джиттером (1 с … 60 с); ошибка проверки TLS или challenge для
  другого адреса останавливают его (78).
- Ограничения Control Plane: 64 КиБ на сообщение, 10 с на аутентификацию, ping каждые 30 с (15 с на ответ),
  30 попыток подключения в минуту с адреса, 256 соединений (32 в процессе аутентификации); браузеры (заголовок
  `Origin`) отклоняются. Обычный `ws://` принимается только с loopback (в Docker — ещё из сети compose,
  `KINDEV_RUNNER_PLAIN_WS_PEERS`); удалённые раннеры используют HTTPS-профиль, где Caddy проксирует WebSocket upgrade.
  `--public-url` / `KINDEV_PUBLIC_URL` (например, `https://ai.example.com`) фиксирует адреса, по которым подключаются
  раннеры; соединение для другого хоста отклоняется (421), поэтому посредник не получит подпись для себя. Отозванный
  или отключённый раннер, не отвечающий на close-фрейм, отрезается через 1 с.
- Канал команд и событий: команды Control Plane (транзакционный журнал раннера, пишется вместе с изменением домена,
  монотонный seq) применяются по одному разу, в порядке commit, и переотправляются до подтверждения. События раннера (accepted, started, output,
  completed, failed) сначала пишутся в спул на диске (`events/`, fsync, 256 МиБ; при переполнении вывод отбрасывается
  и об этом сообщает событие `execution.output.dropped`, события жизненного цикла сохраняются) и удаляются только после
  того, как Control Plane закоммитил и подтвердил их, — обрыв связи или рестарт любой стороны ничего не теряет. Каждое
  событие несёт fencing token попытки: события устаревшего раннера отклоняются, и ему приходит отмена процесса. Каждая
  сессия начинается с `runner.reconcile` (идущие попытки, неподтверждённые результаты, смещения спула).
- Хранение событий раннеров: из незавершённого execution ничего не удаляется. Вывод удаляется через 14 дней после
  завершения execution (`--runner-output-retention-days` / `KINDEV_RUNNER_OUTPUT_RETENTION_DAYS`), остальные события —
  через 30 дней (`--runner-event-retention-days` / `KINDEV_RUNNER_EVENT_RETENTION_DAYS`), подтверждённые команды —
  через 7 дней, весь журнал команд отозванного раннера (он больше не подключится) — в течение часа. Вывод ограничен 16 МиБ на попытку и 1 ГиБ всего (`--runner-output-limit-mb` /
  `KINDEV_RUNNER_OUTPUT_LIMIT_MB`): при превышении сначала вытесняется самый старый вывод завершённых execution, а если
  вывод держат только идущие execution, новый вывод сохраняется без тела (`output_storage_limit`) и в лог пишется
  предупреждение. Очистка идёт при старте и раз в час небольшими батчами.
- Mock-исполнение (пока без ИИ): `POST /api/tasks` создаёт ручную задачу, `POST /api/tasks/{id}/mock-run`
  `{"scenario":"success|fail|flaky|crash|hang|gate"}` планирует её фиксированным планом из одного шага на первом
  репозитории проекта (L1 — запускается без согласования, если политика риска не повысит уровень), `GET
  /api/tasks[/{id}]` показывает задачу с шагами и попытками, `POST /api/tasks/{id}/cancel` `{"reason":"…"}` её
  останавливает. Планировщик назначает READY-шаги только APPROVED, подключённым и доступным раннерам с правом на
  проект, нужными capabilities и без критически заполненного тома; если такого нет, задача `BLOCKED` (причина
  `runner`), пока он не появится. Раннер сам перепроверяет назначение (`ai-runner run --projects <id,…>` /
  `KINDEV_RUNNER_PROJECTS` ограничивает принимаемые проекты) и запускает mock-агента дочерним процессом в своей группе
  процессов; отмена шлёт группе SIGTERM, через 5 с — SIGKILL. Попытка пропавшего раннера становится `UNKNOWN`, когда
  истекает её lease (60 с, продлевается heartbeat), и ничего не перезапускается до reconcile: живой процесс
  продолжается (перезапущенный раннер подхватывает его из журнала `attempts/`), исчезнувший — FAILED и один повтор.
- Хранилище (Owner): на главной видно место на дисках всех машин; **Инфраструктура → Хранилище**
  (`/infrastructure/storage`) добавляет почасовую историю заполнения за 7 или 30 дней с уровнями 75/85/95%, все тома с
  обоими прогнозами и потребителей места. Раннер измеряет потребителей (репозитории, рабочие каталоги и worktree,
  сессии CLI, спул событий, `docker system df`) только при запуске `ai-runner run --measure-space`: раз в 6 ч, только
  метаданные, не быстрее 2 000 записей/с, не более 1 000 000 записей и 10 мин, без симлинков, в пределах одной ФС.
  Ничего не удаляется.

### Интеграции и внешние вызовы

Вызовы YouTrack, GitHub, Telegram и runner никогда не выполняются внутри API-запроса. Исходящие изменения
записываются в durable outbox в той же транзакции SQLite, что и вызвавшее их изменение, и доставляются в фоне
с повторами (экспоненциальный backoff с jitter, после 10 попыток — `dead`); входящие webhooks сохраняются в inbox,
дедуплицируются по delivery id и обрабатываются асинхронно. Поэтому медленный или недоступный сервис не блокирует
dashboard. Owner видит состояние каждого адаптера (`ok`, `degraded`, `circuit_open`) и размеры очередей в
`GET /api/integrations/status`, а `dead`-сообщения — в `GET /api/messaging/{outbox|inbox}/dead`
(`POST …/dead/{id}/retry` ставит сообщение в очередь снова). Доставленные сообщения удаляются через 7 дней, `dead` — через 30.

#### Учётные данные и настройки интеграций

Owner управляет интеграциями на странице **Интеграции**. Подключение к YouTrack (одно на установку) — это базовый
URL и постоянный токен; каждый проект привязывается к проекту YouTrack по короткому имени и имеет реестр
репозиториев GitHub (`owner/name`, интеграционная ветка по умолчанию `dev`; `main` и `master` защищены и не могут
быть интеграционной веткой). Учётные данные шифруются по отдельности ключом установки (AES-256-GCM, имя секрета —
associated data) и доступны только на запись: API сообщает лишь, задан ли токен и когда он обновлён, а пустое поле
токена оставляет сохранённый. **Проверить подключение** ставит проверку в outbox; страница показывает результат,
когда фоновая доставка завершится. Каждое изменение пишется в аудит без секрета. API Owner: `GET /api/integrations`,
`PUT|DELETE /api/integrations/youtrack`, `POST /api/integrations/youtrack/check`, `GET /api/projects/{id}/integrations`,
`PUT /api/projects/{id}/integrations/youtrack`, `POST /api/projects/{id}/repositories`,
`PUT|DELETE /api/projects/{id}/repositories/{repoId}`.

#### Приём задач из YouTrack

Задачи привязанного проекта YouTrack становятся задачами платформы, если у них есть тег-триггер проекта (по
умолчанию `kindevai`, меняется для каждого проекта). **Основной канал — опрос**: каждые 60 с (15–3600 с, задаётся на
странице «Интеграции») Control Plane запрашивает у YouTrack задачи с тегом, изменённые после курсора проекта, кладёт
каждую в надёжный inbox (дедупликация по задаче и `updated`) и только потом сдвигает курсор; повторы и доставки не
по порядку безвредны, а сбои откладывают следующий опрос до 15 минут (с учётом `Retry-After`) и видны в состоянии
интеграции. **Webhook необязателен**: когда Owner задал секрет, workflow YouTrack может вызывать
`POST /api/webhooks/youtrack` с заголовком `X-Kindevai-Webhook-Secret` и телом `{"issueId":"KIN-12","updated":<мс>}`;
платформа сохраняет только ID задачи и перечитывает её через REST API, поэтому тело webhook ничего не решает. Задача
выполняется от имени аккаунта, который Owner связал с логином в YouTrack **того, кто поставил тег-триггер** (берётся
из истории тегов issue, а не автор), и только если этот аккаунт может запускать AI в проекте (Owner или участник
проекта) — создание issue или тег в YouTrack сами ничего не разрешают. Если по истории нельзя точно сказать, кто
поставил тег, задача тоже не создаётся (`tag_not_allowed`); участники видят причину на странице проекта. Участники также могут **запустить задачу по ID** (тег не
нужен, инициатор — сам участник). API: `GET|PUT /api/integrations/youtrack/intake`,
`PUT|DELETE /api/integrations/youtrack/webhook`, `POST /api/integrations/youtrack/users`,
`DELETE /api/integrations/youtrack/users/{userId}`, `PUT /api/projects/{id}/integrations/youtrack/trigger` (Owner);
`GET /api/projects/{id}/youtrack`, `POST /api/projects/{id}/youtrack/runs` (участники).

#### GitHub App

Платформа работает с GitHub только как **GitHub App** (fine-grained PAT — после MVP). На странице **Интеграции**
Owner вводит App ID, закрытый ключ приложения (`.pem`) и секрет вебхука (от 16 символов); оба секрета хранятся в
зашифрованном хранилище и доступны только на запись. Минимальные права приложения — выдавайте только эти:

| Право на репозиторий | Доступ |
|---|---|
| Contents | чтение и запись |
| Pull requests | чтение и запись |
| Checks | чтение |
| Metadata | чтение |

**Не** выдавайте Administration и Workflows: агенты не должны менять настройки репозитория и `.github/workflows`.
Подпишите приложение на события Push, Pull request, Check suite и Check run, укажите URL вебхука
`https://<ваш хост>/api/webhooks/github` и установите приложение только на репозитории, с которыми работает платформа.

- **Installation-токены** выпускаются по запросу через JWT приложения, ограничены одним репозиторием и минимальными правами выше, кешируются
  только в памяти (не дольше 50 минут и не позже чем за 5 минут до истечения) и никогда не сохраняются и не
  логируются. Проект может получить токен только для репозитория, привязанного к этому проекту.
- **Состояние репозитория:** после настройки приложения, регистрации репозитория или нажатия **Обновить** платформа
  в фоне (через outbox) читает, установлено ли приложение, ветку по умолчанию и защищены ли `main`/`master` ruleset'ом
  или branch protection. Для незащищённых `main`/`master` показывается предупреждение — добавьте ruleset, обойти
  который можете только вы.
- **Защита main/master:** независимо от настроек GitHub каждый запрос к GitHub проходит проверку в коде: разрешены
  только известные платформе записи (запрет по умолчанию — никаких GraphQL, настроек и изменений защиты веток), и
  запись отклоняется, если её цель — `main` или `master` (изменение ref, base pull request, merge, коммит файла, в том
  числе без явной ветки). Продвижение в `main`/`master` выполняет только Owner вручную.
- **Вебхуки** (`POST /api/webhooks/github`, без сессии) сначала проверяются по `X-Hub-Signature-256` (HMAC-SHA256,
  сравнение за постоянное время), затем фильтруются по привязанным репозиториям (остальные подтверждаются и
  отбрасываются), сжимаются до небольшого события и сохраняются в durable inbox с дедупликацией по
  `X-GitHub-Delivery`. Неподписанные и поддельные доставки получают 401. Размер тела — до 5 МБ, одновременно читается
  не больше 4.
- URL API GitHub — `--github-api-url` / `KINDEV_GITHUB_API_URL` (по умолчанию `https://api.github.com`; GitHub
  Enterprise Server: `https://<host>/api/v3`).

API Owner: `PUT|DELETE /api/integrations/github`, `POST /api/integrations/github/check`,
`POST /api/projects/{id}/repositories/{repoId}/sync`.

### Сетевые профили и Test Network

**Dashboard → Сеть** (Owner) управляет сетевыми профилями: upstream-прокси (`http://`, `https://` или `socks5://`,
вводится как URL — учётные данные из него извлекаются — или отдельными полями через API), ожидаемый публичный внешний
IPv4/IPv6, режим контроля (`off`, `monitor`, `strict`), политика DNS (резолвер runner или remote DNS через прокси),
fail-closed и список разрешённых адресов (хост, `*.suffix` или CIDR с портами). Пароль прокси хранится зашифрованным
в хранилище учётных данных и никогда не возвращается; в аудите фиксируется только факт его изменения.

Профили назначаются по иерархии **Система → Runner → Проект → CLI**. Нижний уровень может сменить прокси, но не
ослабить защиту: режим, DNS и fail-closed только ужесточаются, список адресов только сужается, поэтому Strict Egress,
включённый для всей установки, ниже снять нельзя. Список адресов не принимает `*`, wildcard верхнего уровня,
`0.0.0.0/0`, `::/0`, слишком широкие префиксы и диапазоны loopback/link-local/multicast. Каждое изменение заново
доставляет runner его итоговые профили командой `runner.config.update` (пароль в журнале команд запечатан и
раскрывается только в аутентифицированной сессии; runner хранит его в файле `0600` и не пишет в логи).

**Test Network** выполняет проверку на runner — доступность и аутентификацию прокси, наблюдаемый внешний IP через
диагностический endpoint (по умолчанию `https://api64.ipify.org`, настраивается в профиле) в сравнении с ожидаемым,
доступность AI-провайдеров, GitHub и YouTrack — и показывает результат, причину ошибки и время. На самой машине
runner: `ai-runner test-network`. Принудительный Strict Egress в песочнице появится в KIN-31.

### Согласования и политика риска

Эффективный риск каждой ревизии плана считает детерминированный **Policy Evaluator**: правила проекта (пути,
миграции, auth/безопасность, схема БД — glob-шаблоны, `**` — любые папки) могут только повысить предложенный AI
уровень, но не понизить. Планы L0/L1 сразу переходят в READY и сливаются в dev по политике; планы L2/L3 ждут Owner на
странице **Согласования**, плюс отдельный запрос *слияние в dev*, который решается после проверки. Решение указывает
ревизию плана и её `planHash`; новая ревизия аннулирует ожидающие согласования, а одобрение старой возвращает 409.
Выполняемый шаг, изменивший файлы вне одобренного scope (или выше одобренного риска), останавливается, пока Owner не
одобрит дополнительные файлы. Решает и меняет политику только Owner; Project Admin видит согласования и политику своих
проектов. API: `GET /api/approvals?state=pending|decided|all`, `GET /api/approvals/{id}`,
`POST /api/approvals/{id}/{approve|reject}` (`planRevision`, `planHash`, `comment` — обязателен при отказе),
`GET/PUT /api/projects/{id}/risk-policy`.
### Журнал аудита

Действия, важные для безопасности, пишутся в журнал аудита (только добавление) в той же транзакции, что и само
действие: завершение первичной настройки; вход, неудачный вход (адрес и причина; логин — только если такая учётная
запись существует, пароль — никогда; попытки, отклонённые ограничителем частоты, не пишутся) и выход; создание,
отключение и включение учётной записи, сброс и смена пароля; создание, отзыв и принятие приглашений; создание проекта,
назначение и снятие роли участника; создание и отзыв токенов регистрации раннеров, регистрация раннера (или отклонённая попытка с известным токеном), одобрение, смена проектов, отключение, включение и отзыв раннера (следующие контексты — approvals, интеграции — добавят свои события). Записи нельзя изменить или
удалить (это запрещают триггеры БД, и API для этого нет); значения, похожие на пароли и токены, сохраняются как
`[redacted]`. Owner читает журнал на странице **Аудит** или через
`GET /api/audit?actor=&project=&kind=&from=&to=&before=&limit=` (сначала новые, `next` — курсор следующей страницы);
остальным пользователям — `403`. Автоочистки в MVP нет.

### Резервное копирование, восстановление и перенос

Автоматических бэкапов в MVP нет; `export`/`import` переносят установку вручную. Control Plane — единственный
экземпляр: кроме lock-файла `data/ai-platform.lock` он держит в базе запись экземпляра (хост, pid, heartbeat), поэтому
второй процесс на тех же данных не стартует — даже через сетевую ФС. Перезапуск на том же хосте
забирает запись сразу; для другого хоста она истекает через 30 секунд после последнего heartbeat, а экземпляр,
потерявший запись, останавливается.

1. **Режим обслуживания** (Owner, пункт меню *Обслуживание*): новые шаги не выдаются, запущенные доработают, раннеры
   продолжают сверку, изменения в UI/API приостановлены для всех (работают вход, вебхуки и действия безопасности:
   отмена задачи, отзыв/отключение раннера, отключение пользователя, отклонение согласования). Баннер
   показывает причину и сколько шагов ещё выполняется. Дождитесь нуля.
2. **Экспорт** (работает при запущенном сервере; онлайн-снимок SQLite, согласованный):
   ```bash
   ai-platform export --data-dir ./data --out backup.tar.gz --key-out backup.key
   # Docker: docker compose exec cp ai-platform export --data-dir /data --out /data/backup.tar.gz --key-out /data/backup.key
   #         docker compose cp cp:/data/backup.tar.gz . && docker compose cp cp:/data/backup.key .
   ```
   Архив содержит манифест (формат, версия, схема, id установки, SHA-256 каждого файла), базу и `data/artifacts/`.
   **Ключа шифрования в архиве нет никогда.** Выбор явный: `--key-out` пишет ключ в отдельный файл 0600,
   `--without-key` не экспортирует его, и вы копируете файл ключа сами. Владелец архива и ключа может прочитать все
   сохранённые секреты — передавайте их разными каналами и удаляйте лишние копии.
3. **Остановите старый Control Plane** (`docker compose down`), чтобы два экземпляра не работали одновременно.
4. **Импорт** в пустой каталог данных на новом хосте:
   ```bash
   ai-platform import --data-dir ./data --archive backup.tar.gz --key backup.key
   # Docker (файлы должны читаться uid 65532):
   # docker compose run --rm --no-deps -v "$PWD:/backup:ro" cp import --data-dir /data --archive /backup/backup.tar.gz --key /backup/backup.key
   ```
   Импорт проверяет манифест, все контрольные суммы, целостность базы, версию схемы (база от более нового бинаря
   отклоняется до любой записи) и соответствие ключа базе. Без ключа он останавливается с ошибкой — новый ключ не
   генерируется. Затем применяются недостающие миграции.
5. **Запустите** новый Control Plane, направьте на него DNS/`--public-url` и выключите режим обслуживания. Раннеры
   переподключатся сами; каждый запуск Control Plane использует новую эпоху канала команд, поэтому восстановленная
   (более старая) база не заставит раннер пропустить новые команды.

## Docker Compose

```bash
docker compose up -d                                        # один контейнер, http://127.0.0.1:8080
DOMAIN=ai.example.com docker compose --profile https up -d  # + Caddy с автоматическим HTTPS на 80/443
docker compose exec cp ai-platform setup-token        # setup token для первой настройки
```

`.env` не нужен. HTTP-порт публикуется только на loopback хоста; публичный доступ — через профиль `https`
(DNS для `DOMAIN` должен указывать на хост). Данные и ключ шифрования лежат в volume `data` — сохраняйте его
целиком. Образ distroless, работает от непривилегированного пользователя с read-only корневой ФС и встроенной
проверкой здоровья (`ai-platform health`).
За Caddy ограничения частоты по клиенту используют `X-Forwarded-For` только от сети compose
(`KINDEV_TRUSTED_PROXIES`, по умолчанию `172.29.240.0/24`; при конфликте задайте `KINDEV_SUBNET`). Базовые образы
закреплены по digest. Без `DOMAIN` профиль https отдаёт `https://localhost` с внутренним CA Caddy.

## Разработка

```bash
make help             # список целей
make dev              # запустить Control Plane на порту этого worktree
npm --prefix web run dev   # Vite dev server, проксирует /api в Control Plane
make test             # Go-тесты (-race -shuffle=on) + unit-тесты web + тесты хуков/скриптов
make lint             # go vet + проверка типов TypeScript
make clean            # удалить артефакты сборки и тестов
```

Ветки создаются от `dev` как `feature/KIN-<n>-<slug>`; pull request — только в `dev`. `main` — только для владельца.

## CI и релизы

| Событие | Что выполняется |
|---|---|
| PR или push в `dev` / `main` | `make lint` (go vet, golangci-lint, oxlint, tsc), тесты с покрытием, `make vuln` (govulncheck, npm audit), `make build`, проверка конфига GoReleaser, actionlint, сборка Docker-образа и смоук-тест |
| Зелёный push в `dev` | **Dev-сборка**: бинарники Control Plane и раннера linux/darwin × amd64/arm64 + `SHA256SUMS` как артефакт прогона CI `ai-platform-dev-<sha>` (хранится 14 дней); образ `ghcr.io/tr1gl1de/kindevai-dev:latest` (отдельный dev-пакет) |
| Тег `v*` на коммите `main` (только владелец) | **Prod-релиз**: проверка, что тег на `main`, тесты, GitHub Release (changelog, checksums, provenance) и образ `:X.Y.Z`, `:X.Y`, `:latest` через защищённый environment `production` |

Автоматизация никогда не пушит в `main` и не создаёт PR в `main`. Dependabot еженедельно предлагает обновления в `dev`.
Все сторонние actions и образы закреплены по SHA/digest.

**Обязательные настройки репозитория (владелец, один раз)** — workflow сами их обеспечить не могут:
1. Rulesets: защитить `main` (push/merge только владелец) и теги `v*` (создавать, менять, удалять — только владелец).
2. Environment `production`: обязательный ревьюер — владелец, без обхода администраторами, deployment tags `v*`.
3. Пакет `ghcr.io/tr1gl1de/kindevai`: права записи из Actions только для этого репозитория (dev-образы — в
   `kindevai-dev`).
Локально: `make lint vuln build`, `make release-snapshot` (нужен GoReleaser).
