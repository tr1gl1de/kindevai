# Kindevai

**Коллективный интеллект. Индивидуальная забота.** Платформа автономной AI-разработки.

[English version](README.md)

Kindevai — self-hosted платформа, которая превращает задачи YouTrack в изменения кода. Код пишут AI CLI (Codex, Claude
Code, ZCode) на внешних runners по правилам согласования владельца. Проект в активной разработке; спецификация
находится в Knowledge Base YouTrack (проект `KIN`, корневая статья `KIN-A-1`).

## Архитектура кратко

- **Control Plane** — один Go-процесс (модульный монолит), SQLite в режиме WAL, React Dashboard встроен через
  `go:embed`. Цель — VPS 1 vCPU / 1 GB RAM. Без PostgreSQL, Redis, Temporal и RabbitMQ.
- **Runner** — Go-демон для Linux/WSL2/macOS; подключается к Control Plane исходящим WSS и запускает AI CLI
  в изолированных git worktree.
- **Web UI** — React + TypeScript, работает и как Telegram Mini App.

## Структура репозитория

| Путь | Содержимое |
|---|---|
| `cmd/ai-platform` | Бинарник Control Plane (`serve`, `version`) |
| `cmd/ai-runner` | Демон раннера (`enroll`, `fingerprint`, `run`, `version`) |
| `internal/` | Go-пакеты Control Plane (`internal/runner/...` — раннер, `internal/protocol` — общие wire-сообщения) |
| `web/` | Dashboard на React + TypeScript (Vite); `web/embed.go` встраивает сборку |
| `docs/brand/` | Фирменные материалы: логотип Kindevai, знак и wordmark (SVG; светлый, тёмный, монохромный) |
| `scripts/` | Вспомогательные скрипты (worktree задач, учёт времени, замер нагрузки `measure-cp.sh`) |
| `.claude/` | Правила, агенты и skills Claude Code для разработки репозитория |

## Требования

Go (версия в `go.mod`), Node.js 24+ и npm (только для сборки web UI), `make`.

## Быстрый старт

```bash
make build            # собирает web/dist/app, затем bin/ai-platform со встроенным UI
./bin/ai-platform serve   # http://127.0.0.1:8080
```

`ai-platform serve --addr 127.0.0.1:9000` меняет адрес. Бинарник, собранный без web UI, тоже запускается
и показывает страницу-заглушку.

Для развёртывания на сервере следуйте разделу [Установка](#установка).

### Каталог данных и ключ шифрования

При первом запуске `serve` создаёт `./data` (флаг `--data-dir`), SQLite в режиме WAL (`data/db/platform.db`),
применяет миграции схемы и генерирует ключ шифрования `data/secrets/master.key` (права 0600; `--key-file` позволяет
хранить его в другом месте). Следующие запуски используют существующие данные. **Берегите ключ — без него резервная копия бесполезна (см. «Резервное копирование, восстановление и перенос»):**
если база есть, а ключа нет или он другой, Control Plane не запустится и никогда не создаст ключ взамен.
Каталог данных одновременно может использовать только один процесс.

### Первая настройка

Новая установка стартует в режиме setup. Для создания первого Owner нужен одноразовый **setup token**. Он никогда
не выводится в логи и не отдаётся по HTTP: он записывается в `data/secrets/setup-token` (права 0600; в логе только
путь). Прочитайте его на хосте (`ai-platform setup-token` или `docker compose exec cp ai-platform setup-token`)
и введите в мастере Dashboard вместе с логином Owner, паролем (от 12 символов) и названием платформы. Токен
действует час и обновляется автоматически; после настройки он удаляется, и повторить setup нельзя — в том числе
после рестарта.

### Вход

После настройки войдите с логином и паролем Owner. Сессии хранятся на сервере: браузер получает cookie HttpOnly,
SameSite=Strict (Secure при HTTPS); сессия завершается после 12 часов бездействия, не позже чем через 7 дней,
или при выходе. Все API, кроме health, setup, входа, принятия приглашения и регистрации раннера, требуют сессию; изменяющие запросы с чужого origin
отклоняются, попытки входа ограничены по адресу и по учётной записи.

### Проекты и доступ

Owner создаёт проекты и выдаёт участие (`project_admin` или `member`); в MVP участниками управляет только Owner.
Пользователь видит только свои проекты — любой другой отвечает `404`, так же как несуществующий. API:
`GET/POST /api/projects`, `GET /api/projects/{id}`, `GET /api/projects/{id}/members`,
`PUT/DELETE /api/projects/{id}/members/{login}`.

### Раннеры

Owner добавляет машину на странице **Раннеры**: **Добавить раннер** показывает одноразовый токен регистрации (256 бит,
действует 10 минут, хранится только SHA-256) и команду для этой машины — `ai-runner enroll --server <URL>`; токен она
запрашивает через stdin, поэтому он не попадает в argv и историю shell. Раннер создаёт пару ключей Ed25519 и регистрирует
открытый ключ через публичный `POST /api/runners/enroll` с ограничением частоты; раннер получает статус **ожидает
одобрения** и не может подключаться и получать работу. Owner сверяет отпечаток в стиле OpenSSH (`SHA256:…`, как у
`ssh-keygen -lf`) с выводом `ai-runner fingerprint` на машине и одобряет раннер для явного списка проектов; позже
можно менять проекты, отключать/включать и отзывать раннер (отзыв окончателен; повторная регистрация — с новым ключом).
Удалённым раннерам нужен HTTPS (профиль Caddy); обычный HTTP — только для раннера на том же хосте. API Owner:
`POST/GET /api/runners/enrollment-tokens`, `POST /api/runners/enrollment-tokens/{id}/revoke`, `GET /api/runners`,
`GET /api/runners/{id}`, `POST /api/runners/{id}/{approve|disable|enable|revoke}`, `PUT /api/runners/{id}/projects`.

### Демон раннера (`ai-runner`)

`ai-runner` — второй бинарник (`cmd/ai-runner`, linux/darwin × amd64/arm64, архивы релиза
`kindevai-runner_<версия>_<os>_<arch>.tar.gz`). Команды: `enroll`, `fingerprint`, `run`, `version`.

```bash
ai-runner enroll --server https://kindevai.example.com   # спросит токен без отображения ввода
ai-runner fingerprint                                    # сверьте с карточкой раннера перед одобрением
```

- Токен читается из скрытого prompt, из stdin (`… | ai-runner enroll --server …`) или из `--token-file <путь>`
  (файл с правами 0600); `--token` и позиционные аргументы отклоняются.
- Ключ Ed25519 создаётся один раз при первом `enroll` (`keys/ed25519.pem`, PKCS#8, права 0600) и никогда не
  заменяется: повреждённый ключ — ошибка, а ключ или конфиг, доступные другим пользователям, отклоняются (`chmod 600`).
  Повтор с тем же токеном после обрыва использует тот же ключ. Fingerprint, который вернул Control Plane, обязан
  совпасть с локальным ключом, иначе регистрация не сохраняется.
- Сертификаты TLS проверяются всегда; флага insecure нет. `http://` работает только для Control Plane на
  `localhost`/loopback, и соединение по http возможно только с loopback-адресом. Переменные прокси (`HTTPS_PROXY`) для канала управления игнорируются, редиректы не выполняются.
- Каталог данных (`--data-dir`): `/var/lib/kindevai-runner` под root, иначе `$XDG_DATA_HOME/kindevai-runner` или
  `~/.local/share/kindevai-runner`. В нём `config.json` (сервер, id раннера, fingerprint; 0600), `keys/` и
  `repos/ workspaces/ sessions/ events/ proxy/`, все с правами 0700; одновременно — только один процесс (lock-файл).
- Сервисы: `deploy/runner/kindevai-runner.service` (системный сервис systemd под отдельным пользователем),
  `kindevai-runner-user.service` (пользовательский сервис systemd, например в WSL2, чтобы AI CLI использовали ваши
  логины) и `io.kindevai.runner.plist` (агент launchd для macOS); шаги установки — в каждом файле. Остановка или
  перезапуск сервиса останавливает только демон (`KillMode=process`, в launchd `AbandonProcessGroup`): идущие попытки
  продолжаются, и следующий запуск их подхватывает, узнавая процесс по pid и времени старта, поэтому переиспользованный
  pid никогда не принимается за него. Чтобы остановить и попытки, отключите раннер в Dashboard или используйте
  `systemctl kill` (KIN-64).
- `ai-runner run` держит исходящий WebSocket к `wss://<сервер>/runner/connect` (`ws://` — только для Control Plane на
  loopback). Каждое подключение проходит challenge-response: Control Plane присылает одноразовый 32-байтный nonce,
  привязанный к id соединения и своему адресу, раннер подписывает
  `kindevai-runner-auth/1\n<id раннера>\n<audience>\n<nonce>\n<срок>\n<id соединения>` своим ключом Ed25519, и
  впускается только **одобренный** раннер (ожидающий/отключённый получает отказ и повторяет попытки, отозванный
  останавливает демон с кодом 78). Отключение или отзыв раннера сразу закрывает его активное соединение и в той же
  транзакции проваливает его идущие попытки (повтор на другом раннере); раннер сам останавливает их процессы, как только
  узнаёт об отключении или отзыве, не дожидаясь Control Plane (KIN-63). Раннер
  переподключается с экспоненциальной задержкой с джиттером (1 с … 60 с); ошибка проверки TLS или challenge для
  другого адреса останавливают его (78).
- Ограничения Control Plane: 64 КиБ на сообщение, 10 с на аутентификацию, ping каждые 30 с (15 с на ответ),
  30 попыток подключения в минуту с адреса, 256 соединений (32 в процессе аутентификации); браузеры (заголовок
  `Origin`) отклоняются. Обычный `ws://` принимается только с loopback (в Docker — ещё из сети compose,
  `KINDEV_RUNNER_PLAIN_WS_PEERS`); удалённые раннеры используют HTTPS-профиль, где Caddy проксирует WebSocket upgrade.
  `--public-url` / `KINDEV_PUBLIC_URL` (например, `https://ai.example.com`) фиксирует адреса, по которым подключаются
  раннеры; соединение для другого хоста отклоняется (421), поэтому посредник не получит подпись для себя. Отозванный
  или отключённый раннер, не отвечающий на close-фрейм, отрезается через 1 с.
- Канал команд и событий: команды Control Plane (транзакционный журнал раннера, пишется вместе с изменением домена,
  монотонный seq) применяются по одному разу, в порядке commit, и переотправляются до подтверждения. События раннера (accepted, started, output,
  completed, failed) сначала пишутся в спул на диске (`events/`, fsync, 256 МиБ; при переполнении вывод отбрасывается
  и об этом сообщает событие `execution.output.dropped`, события жизненного цикла сохраняются) и удаляются только после
  того, как Control Plane закоммитил и подтвердил их, — обрыв связи или рестарт любой стороны ничего не теряет. Каждое
  событие несёт fencing token попытки: события устаревшего раннера отклоняются, и ему приходит отмена процесса. Каждая
  сессия начинается с `runner.reconcile` (идущие попытки, неподтверждённые результаты, смещения спула).
- Секреты в выводе раннера: раннер маскирует известные ему секреты (git-токен назначения, пароли прокси) по точному
  значению и секреты по форме (токены, API-ключи, пароли в URL, пары `key=value`, PEM-ключи) до записи вывода в
  спул, придерживая неполную строку (не более 8 KiB, до 1 с), чтобы маскировать и секрет, разрезанный между
  записями; Control Plane ещё раз маскирует каждый фрагмент вывода и причину сбоя перед сохранением и снова при
  чтении в интерфейсе задачи. Строки сохраняются: замаскированное значение заменяется на `[redacted]` на месте.
- Хранение событий раннеров: из незавершённого execution ничего не удаляется. Вывод удаляется через 14 дней после
  завершения execution (`--runner-output-retention-days` / `KINDEV_RUNNER_OUTPUT_RETENTION_DAYS`), остальные события —
  через 30 дней (`--runner-event-retention-days` / `KINDEV_RUNNER_EVENT_RETENTION_DAYS`), подтверждённые команды —
  через 7 дней, весь журнал команд отозванного раннера (он больше не подключится) — в течение часа. Вывод ограничен 16 МиБ на попытку и 1 ГиБ всего (`--runner-output-limit-mb` /
  `KINDEV_RUNNER_OUTPUT_LIMIT_MB`): при превышении сначала вытесняется самый старый вывод завершённых execution, а если
  вывод держат только идущие execution, новый вывод сохраняется без тела (`output_storage_limit`) и в лог пишется
  предупреждение. Очистка идёт при старте и раз в час небольшими батчами.
- Mock-исполнение (пока без ИИ): `POST /api/tasks` создаёт ручную задачу, `POST /api/tasks/{id}/mock-run`
  `{"scenario":"success|fail|flaky|crash|hang|gate"}` планирует её фиксированным планом из одного шага на первом
  репозитории проекта (L1 — запускается без согласования, если политика риска не повысит уровень), `GET
  /api/tasks[/{id}]` показывает задачу с шагами и попытками, `POST /api/tasks/{id}/cancel` `{"reason":"…"}` её
  останавливает. Планировщик назначает READY-шаги только APPROVED, подключённым и доступным раннерам с правом на
  проект, нужными capabilities и без критически заполненного тома; если такого нет, задача `BLOCKED` (причина
  `runner`), пока он не появится. Из них предпочитается раннер без 2+ упавших или потерянных попыток за последний час,
  затем с более свободным диском (ok, warning, high), затем с меньшим числом занятых шагов; раннер, запущенный с
  `ai-runner run --max-parallel-steps N`, получает не больше N шагов workflow одновременно (запуски планировщика не
  считаются; шаг, который могли бы взять только такие заполненные раннеры, ждёт как `WAITING(runner)`). Раннер сам перепроверяет назначение (`ai-runner run --projects <id,…>` /
  `KINDEV_RUNNER_PROJECTS` ограничивает принимаемые проекты) и запускает mock-агента дочерним процессом в своей группе
  процессов; отмена шлёт группе SIGTERM, через 5 с — SIGKILL. Попытка пропавшего раннера становится `UNKNOWN`, когда
  истекает её lease (60 с, продлевается heartbeat), и ничего не перезапускается до reconcile: живой процесс
  продолжается (перезапущенный раннер подхватывает его из журнала `attempts/`), исчезнувший — FAILED и один повтор.
- Задачи и исполнения (`/tasks`, KIN-25): список задач с фильтрами по проекту и состоянию и страница задачи с
  ревизией плана, шагами по этапам, попытками (runner, CLI) и выводом и событиями каждой попытки (опрос ограниченными
  страницами). Owner и администраторы проекта создают задачи, планируют их mock-планировщиком, отменяют и повторяют
  упавшие (`POST /api/tasks/{id}/retry`: текущий план становится новой ревизией и снова проходит политику риска).
  **Время агентов** — время работы CLI-процессов агентов (от `execution.started` до completed/failed по часам runner,
  записывается один раз на попытку); показывается по попытке, шагу, задаче и фильтру списка, отдельно от календарной
  длительности задачи. Период без конца (процесс потерян) или без пригодного времени показывается как «учёт неполный»,
  а не как успешная запись.
- Агенты (`/agents` для владельца, блок «AI-агенты» в проекте для владельца и админов проекта, KIN-33): включение и
  выключение каждого AI CLI (Claude Code, Codex) глобально и в проекте — проект не может включить CLI, выключенный
  владельцем, — и привязка ролей планировщика, исполнителя и ревьюера к CLI и модели с упорядоченными резервными
  (ревьюер предпочитает CLI, отличный от автора). Планировщик запускает шаг на первом разрешённом CLI, который установлен
  на подходящем runner и не ждёт сброса лимита; иначе задача `BLOCKED` с причиной (`agent`, `cli_limit` или `runner`).
  Выключение даёт текущим сессиям доработать; **аварийная остановка** отменяет и их.
- AI-планировщик (KIN-34): «Спланировать с AI» на странице задачи (`POST /api/tasks/{id}/plan`, Owner / администратор
  проекта) запускает CLI, назначенный на роль планировщика, на раннере — только чтение в worktree первого репозитория
  проекта (без scope, никогда без обхода разрешений). Пакет контекста: задача, текст issue из YouTrack и до 3 связанных
  статей базы знаний (читаются через outbox, ограничены по размеру, помечены как недоверенный текст, который не меняет
  правила, scope и права) и JSON Schema плана (`internal/workflow/domain/plan.schema.json`, v1: DAG шагов, репозитории,
  scope, риск, контракты, миграции, тесты, документация). Ответ разбирается строго; валидный план становится следующей
  ревизией через политику рисков (L0/L1 — READY, L2/L3 — согласование), невалидный получает один повтор с причиной,
  затем задача FAILED с причиной. Native session планировщика сохраняется: повтор или перепланирование на том же раннере
  и чат по плану продолжают её. `KINDEV_REAL_CLI_SMOKE=1 go test -run TestRealCLIPlannerSmoke ./cmd/ai-platform/`
  запрашивает настоящий план у установленного Claude CLI.
- Реализация и независимое ревью (KIN-35): шаг плана на AI CLI проходит цикл на своей рабочей ветке
  `feature/<task>--<step>`. Исполнитель получает утверждённый шаг (название задачи и текст плана — как недоверенный
  текст, scope, тесты из плана, команду тестов репозитория) и завершает работу передачей (итог, влияние на
  документацию, открытые вопросы). После CLI `agent-exec` запускает **команду тестов** репозитория (Проект →
  Репозитории, например `make test`) через `/bin/sh` в worktree, в той же изоляции, что и попытка, с ограниченным
  окружением (без учётных данных CLI); раннер сообщает код выхода, длительность и конец вывода (`execution.tests`) —
  заявление модели доказательством не считается. Упавшие тесты или отсутствие результата проваливают попытку (один
  повтор с выводом), отсутствие команды показывается как «не настроены». Затем ревьюер запускается на том же раннере
  (там ветка) на CLI, отличном от автора, если маршрутизация позволяет, только на чтение (Claude
  `--permission-mode default` без инструментов записи и shell, Codex `--sandbox read-only`), с ограниченным diff
  base..head в промпте; ответ — JSON-вердикт `approve | changes_requested` с замечаниями. Запрошенные исправления
  запускают раунд исправлений с замечаниями (не более 2), после чего шаг FAILED с причиной; ревьюер, изменивший ветку,
  проваливает попытку. Страница задачи показывает фазу, передачу (base/head, изменённые файлы, доказательство тестов) и
  вердикт. Push и PR — KIN-36.
- Цикл исправления CI и мерж в dev (KIN-37): Control Plane следит за CI каждого открытого им пул-реквеста
  (завершённые check suites из вебхука GitHub плюс сверка раз в минуту; статус объединяет все последние check runs
  head — если их ещё нет или какой-то выполняется, статус pending). Такой CI не поднимает алертов в Alert Center.
  Красный CI переоткрывает выполнение: шаг снова реализуется на раннере, где лежит его ветка, с перечнем упавших
  проверок, проходит ревью и снова пушится (fast-forward) — не более 3 раундов исправления CI на шаг, затем задача
  BLOCKED (причина `ci`) с алертом; последующий зелёный перезапуск возобновляет её. Зелёный CI проходит через шлюз
  мержа: integrate_dev разрешён политикой (L0/L1) или одобрен Owner (L2/L3) — без этого ничего не мержится, у PR
  «мерж ожидает». Мерж — merge commit с ожидаемым head SHA (сдвинутый head, конфликт или защищённая база не мержатся:
  задача BLOCKED с причиной); change set из нескольких репозиториев мержится по порядку и останавливается на первой
  ошибке. Когда все PR смержены, задача COMPLETED. `main`/`master` никогда не цель мержа.
- Задачи, ждущие CI, и репозитории без CI (KIN-105): репозиторий без CI никогда не мержится автоматически — у head без
  единой проверки видно «Нет проверок CI», а через 30 минут без них задача BLOCKED (причина `ci`). У задачи, ждущей CI,
  Owner или администратор проекта может нажать **Возобновить** (`POST /api/tasks/{id}/resume`: CI проверяется сразу,
  красный CI снова блокирует, репозиторий без CI получает ещё 30 минут) или **Повторить мерж**
  (`POST /api/tasks/{id}/retry-merge`, после отклонённого мержа). Ни то, ни другое не обходит шлюз мержа. Устаревшие
  commit statuses не читаются: CI должен публиковать check runs (GitHub Actions так и делает).
- Раунды исправления CI на практике (KIN-106): исполнитель раунда получает не только имена упавших проверок, но и их
  вывод (title и summary, с ограничением размера, как недоверенный текст); аудит, причина блокировки и карточка PR
  показывают только имена (summary может повторять строки логов). Если раннер, у которого лежит ветка шага, отключён
  или отозван, раунд продолжается на другом раннере от опубликованного head удалённой ветки (она подтягивается в его
  кэш), поэтому push остаётся fast-forward; ветку, которую сдвинул кто-то другой, платформа не перезаписывает. Раннер,
  который просто ушёл offline, держит шаг до возвращения — чтобы перенести работу, отключите его. Когда задача входит в VERIFYING с ожидающим одобрением integrate_dev (L2/L3),
  Owner получает в Telegram уведомление, что проверенная работа ждёт мержа в dev.
- API обсуждения плана (KIN-43; UI чата — KIN-44): Owner и администраторы проекта пишут о текущей ревизии плана задачи,
  ожидающей согласования или готовой к запуску (`POST /api/tasks/{id}/discussion/messages`, 202; участники и
  наблюдатели читают `GET /api/tasks/{id}/discussion`). Каждое сообщение — ход, который CLI роли планировщика выполняет
  как попытку планировщика (durable-журнал команд раннера, только чтение, без scope): продолжает native session
  планировщика на её раннере или начинает новую с планом, пакетом контекста и последними 20 сообщениями — всё как
  недоверенный текст. Ответ сохраняется с расходом и временем CLI (время агента); план в блоке ```json становится
  следующей ревизией через валидацию плана и политику рисков (AI не может понизить риск; согласования старой ревизии
  устаревают), невалидный отмечается и игнорируется. Статус PENDING → DELIVERED → ANSWERED | FAILED; ход без ответа
  после таймаута FAILED, сообщение можно отправить снова (`…/messages/{msg}/retry`). Лимиты (Owner:
  `PUT /api/plan-discussion/limits`): 4000 символов, один ответ в работе, 20 сообщений на задачу, 30 в час на
  пользователя, таймаут 10 мин; превышение — 429 с кодом причины. Сообщения, ответы, ревизии и срабатывания лимитов
  пишутся в аудит.
- AI CLI (раннер, KIN-79): назначение для `claude` или `codex` (выбор маршрутизации) запускает CLI из PATH раннера с
  HOME пользователя раннера (его локальный вход) и чистым окружением, как `ai-runner agent-exec` в группе процессов
  попытки: промпт/пакет контекста — файл в каталоге состояния попытки (вне worktree), читается со stdin, вывод CLI
  пишется в файлы там же (после рестарта раннер дочитывает их, ничего не отправляется дважды), таймаут (по умолчанию
  2 ч) действует и без раннера. Обход разрешений даётся только внутри проверенной песочницы strict egress (KIN-31),
  в остальных случаях — отказ. Типизированные события CLI (сессия, текст, вызов инструмента, результат, ошибка) видны в
  логе попытки; расход (токены, стоимость, ходы), native session id и версия CLI хранятся по попытке и показываются
  рядом с агентским временем. Лимит или разлогин (`cli_limit`) ставит шаг на ожидание и задачу в BLOCKED (причина
  `cli_limit`, алерт) до сброса лимита (30 мин, если CLI не назвал время) — или сразу на другом разрешённом CLI или раннере, пока CLI
  этого раннера «остывает». CLI без входа в аккаунт или с отказом оплаты повторяется через 30 мин, 2 ч и 6 ч, затем
  ждёт отметки Owner «снова готов» на странице «Агенты»; его алерт называет раннер и CLI и становится критичным на
  третьем отказе подряд.
- Рабочие каталоги (раннер): если репозиторий шага зарегистрирован в проекте, попытка работает в собственном git
  worktree в `workspaces/` на ветке `feature/<task>--<step>` (никогда не main/master) от интеграционной ветки
  репозитория, загруженной в bare-кэш в `repos/`; базовый коммит фиксируется. Control Plane добавляет ветку и
  короткоживущий installation-токен только этого репозитория в назначение лишь в момент отправки; раннер передаёт
  токен git только через свой credential helper (`ai-runner git-credential`, unix-сокет раннера на время fetch) и
  только хосту из `--git-base-url` (по умолчанию `https://github.com`, `KINDEV_RUNNER_GIT_BASE_URL`): не в
  аргументах, окружении, файлах или URL remote. Файлы инструкций (`AGENTS.md`, `CLAUDE.md`,
  `.claude/{agents,skills,rules,commands,settings*}`, `.codex/`, `.mcp.json`) передаются с SHA-256 как недоверенные
  данные (симлинки не разыменовываются, содержимое не разбирается). По завершении незакоммиченная работа
  коммитится в ветку, отправляются изменённые относительно базы файлы и изменившиеся инструкции, worktree
  удаляется, ветка остаётся. Один writer на workspace; нужно не меньше `--workspace-min-free-mib` (по умолчанию
  2048) свободного места на файловой системе каталога данных.
- Хранилище (Owner): на главной видно место на дисках всех машин; **Инфраструктура → Хранилище**
  (`/infrastructure/storage`) добавляет почасовую историю заполнения за 7 или 30 дней с уровнями 75/85/95%, все тома с
  обоими прогнозами и потребителей места. Раннер измеряет потребителей (репозитории, рабочие каталоги и worktree,
  сессии CLI, спул событий, `docker system df`) только при запуске `ai-runner run --measure-space`: раз в 6 ч, только
  метаданные, не быстрее 2 000 записей/с, не более 1 000 000 записей и 10 мин, без симлинков, в пределах одной ФС.
  Ничего не удаляется.

### Интеграции и внешние вызовы

Вызовы YouTrack, GitHub, Telegram и runner никогда не выполняются внутри API-запроса. Исходящие изменения
записываются в durable outbox в той же транзакции SQLite, что и вызвавшее их изменение, и доставляются в фоне
с повторами (экспоненциальный backoff с jitter, после 10 попыток — `dead`); входящие webhooks сохраняются в inbox,
дедуплицируются по delivery id и обрабатываются асинхронно. Поэтому медленный или недоступный сервис не блокирует
dashboard. Owner видит состояние каждого адаптера (`ok`, `degraded`, `circuit_open`) и размеры очередей в
`GET /api/integrations/status`, а `dead`-сообщения — в `GET /api/messaging/{outbox|inbox}/dead`
(`POST …/dead/{id}/retry` ставит сообщение в очередь снова). Доставленные сообщения удаляются через 7 дней, `dead` — через 30.

#### Учётные данные и настройки интеграций

Owner управляет интеграциями на странице **Интеграции**. Подключение к YouTrack (одно на установку) — это базовый
URL и постоянный токен; каждый проект привязывается к проекту YouTrack по короткому имени и имеет реестр
репозиториев GitHub (`owner/name`, интеграционная ветка по умолчанию `dev`; `main` и `master` защищены и не могут
быть интеграционной веткой). Учётные данные шифруются по отдельности ключом установки (AES-256-GCM, имя секрета —
associated data) и доступны только на запись: API сообщает лишь, задан ли токен и когда он обновлён, а пустое поле
токена оставляет сохранённый. **Проверить подключение** ставит проверку в outbox; страница показывает результат,
когда фоновая доставка завершится. Каждое изменение пишется в аудит без секрета. API Owner: `GET /api/integrations`,
`PUT|DELETE /api/integrations/youtrack`, `POST /api/integrations/youtrack/check`, `GET /api/projects/{id}/integrations`,
`PUT /api/projects/{id}/integrations/youtrack`, `POST /api/projects/{id}/repositories`,
`PUT|DELETE /api/projects/{id}/repositories/{repoId}`.

#### Приём задач из YouTrack

Задачи привязанного проекта YouTrack становятся задачами платформы, если у них есть тег-триггер проекта (по
умолчанию `kindevai`, меняется для каждого проекта). **Основной канал — опрос**: каждые 60 с (15–3600 с, задаётся на
странице «Интеграции») Control Plane запрашивает у YouTrack задачи с тегом, изменённые после курсора проекта, кладёт
каждую в надёжный inbox (дедупликация по задаче и `updated`) и только потом сдвигает курсор; повторы и доставки не
по порядку безвредны, а сбои откладывают следующий опрос до 15 минут (с учётом `Retry-After`) и видны в состоянии
интеграции. **Webhook необязателен**: когда Owner задал секрет, workflow YouTrack может вызывать
`POST /api/webhooks/youtrack` с заголовком `X-Kindevai-Webhook-Secret` и телом `{"issueId":"KIN-12","updated":<мс>}`;
платформа сохраняет только ID задачи и перечитывает её через REST API, поэтому тело webhook ничего не решает. Задача
выполняется от имени аккаунта, который Owner связал с логином в YouTrack **того, кто поставил тег-триггер** (берётся
из истории тегов issue, а не автор), и только если этот аккаунт может запускать AI в проекте (Owner или участник
проекта) — создание issue или тег в YouTrack сами ничего не разрешают. Если по истории нельзя точно сказать, кто
поставил тег, задача тоже не создаётся (`tag_not_allowed`); участники видят причину на странице проекта. Участники также могут **запустить задачу по ID** (тег не
нужен, инициатор — сам участник). API: `GET|PUT /api/integrations/youtrack/intake`,
`PUT|DELETE /api/integrations/youtrack/webhook`, `POST /api/integrations/youtrack/users`,
`DELETE /api/integrations/youtrack/users/{userId}`, `PUT /api/projects/{id}/integrations/youtrack/trigger` (Owner);
`GET /api/projects/{id}/youtrack`, `POST /api/projects/{id}/youtrack/runs` (участники).

#### Обратная запись в YouTrack

Задача из YouTrack сообщает о себе в issue от имени интеграционного пользователя (токен подключения): комментарий с
принятым планом (кратко, риск, шаги) и ссылкой на его утверждение на странице задачи (`--public-url`), каждую смену
состояния, если проект сопоставил состояния задач со статусами YouTrack, и финальный комментарий с пул-реквестами,
агентским временем (время процессов CLI) и решением по документации. По умолчанию сопоставление пустое — пишутся
только комментарии; Owner или администратор проекта задаёт его в блоке **Статусы YouTrack** на странице проекта (поле
на каждое состояние задачи; пустое — статус issue не меняется) или через `PUT /api/projects/{id}/integrations/youtrack/states`
(`{"states":{"RUNNING":"In Progress","COMPLETED":"Fixed"}}`). Записи одной задачи доходят до YouTrack по одной в
порядке их создания, поэтому финальный комментарий никогда не опережает смену статуса. Каждая запись — сообщение outbox с ключом изменения
(correlation id): комментарий несёт маркер `kindev-…`, поэтому повтор после потерянного ответа не дублирует его, а
собственные записи платформы, вернувшиеся через вебхук или опрос, не создают новых задач. Пока YouTrack недоступен,
записи повторяются, а на странице задачи видно **Ожидает публикации в YouTrack**; брошенные записи показываются как
неопубликованные с причиной и поднимают в Alert Center алерт «Запись в YouTrack не удалась», который закрывается,
когда следующая запись задачи опубликована. Исполнитель может обновить разделы Базы знаний — только статей, указанных в
утверждённом плане как затрагиваемая документация, — или указать `docsNotApplicable` с причиной (`DOCS_NOT_APPLICABLE`);
решение сохраняется и показывается на странице задачи. Раздел пересчитывается по статье в её состоянии прямо перед
записью; параллельная правка приводит к повторному чтению и пересчёту (после трёх конфликтов запись помечается
неудавшейся).

#### GitHub App

Платформа работает с GitHub только как **GitHub App** (fine-grained PAT — после MVP). На странице **Интеграции**
Owner вводит App ID, закрытый ключ приложения (`.pem`) и секрет вебхука (от 16 символов); оба секрета хранятся в
зашифрованном хранилище и доступны только на запись. Минимальные права приложения — выдавайте только эти:

| Право на репозиторий | Доступ |
|---|---|
| Contents | чтение и запись |
| Pull requests | чтение и запись |
| Checks | чтение |
| Metadata | чтение |

**Не** выдавайте Administration и Workflows: агенты не должны менять настройки репозитория и `.github/workflows`.
Подпишите приложение на события Push, Pull request, Check suite и Check run, укажите URL вебхука
`https://<ваш хост>/api/webhooks/github` и установите приложение только на репозитории, с которыми работает платформа.

- **Installation-токены** выпускаются по запросу через JWT приложения, ограничены одним репозиторием и минимальными правами выше, кешируются
  только в памяти (не дольше 50 минут и не позже чем за 5 минут до истечения) и никогда не сохраняются и не
  логируются. Проект может получить токен только для репозитория, привязанного к этому проекту.
- **Состояние репозитория:** после настройки приложения, регистрации репозитория или нажатия **Обновить** платформа
  в фоне (через outbox) читает, установлено ли приложение, ветку по умолчанию и защищены ли `main`/`master` ruleset'ом
  или branch protection. Для незащищённых `main`/`master` показывается предупреждение — добавьте ruleset, обойти
  который можете только вы.
- **Защита main/master:** независимо от настроек GitHub каждый запрос к GitHub проходит проверку в коде: разрешены
  только известные платформе записи (запрет по умолчанию — никаких GraphQL, настроек и изменений защиты веток), и
  запись отклоняется, если её цель — `main` или `master` (изменение ref, base pull request, merge, коммит файла, в том
  числе без явной ветки). Продвижение в `main`/`master` выполняет только Owner вручную.
- **Вебхуки** (`POST /api/webhooks/github`, без сессии) сначала проверяются по `X-Hub-Signature-256` (HMAC-SHA256,
  сравнение за постоянное время), затем фильтруются по привязанным репозиториям (остальные подтверждаются и
  отбрасываются), сжимаются до небольшого события и сохраняются в durable inbox с дедупликацией по
  `X-GitHub-Delivery`. Неподписанные и поддельные доставки получают 401. Размер тела — до 5 МБ, одновременно читается
  не больше 4.
- URL API GitHub — `--github-api-url` / `KINDEV_GITHUB_API_URL` (по умолчанию `https://api.github.com`; GitHub
  Enterprise Server: `https://<host>/api/v3`).

API Owner: `PUT|DELETE /api/integrations/github`, `POST /api/integrations/github/check`,
`POST /api/projects/{id}/repositories/{repoId}/sync`.

### Сетевые профили и Test Network

**Dashboard → Сеть** (Owner) управляет сетевыми профилями: upstream-прокси (`http://`, `https://` или `socks5://`,
вводится как URL — учётные данные из него извлекаются — или отдельными полями через API), ожидаемый публичный внешний
IPv4/IPv6, режим контроля (`off`, `monitor`, `strict`), политика DNS (резолвер runner или remote DNS через прокси),
fail-closed и список разрешённых адресов (хост, `*.suffix` или CIDR с портами). Пароль прокси хранится зашифрованным
в хранилище учётных данных и никогда не возвращается; в аудите фиксируется только факт его изменения.

Профили назначаются по иерархии **Система → Runner → Проект → CLI**. Нижний уровень может сменить прокси, но не
ослабить защиту: режим, DNS и fail-closed только ужесточаются, список адресов только сужается, поэтому Strict Egress,
включённый для всей установки, ниже снять нельзя. Список адресов не принимает `*`, wildcard верхнего уровня,
`0.0.0.0/0`, `::/0`, слишком широкие префиксы и диапазоны loopback/link-local/multicast. Каждое изменение заново
доставляет runner его итоговые профили командой `runner.config.update` (пароль в журнале команд запечатан и
раскрывается только в аутентифицированной сессии; runner хранит его в файле `0600` и не пишет в логи).

**Test Network** выполняет проверку на runner — доступность и аутентификацию прокси, наблюдаемый внешний IP через
диагностический endpoint (по умолчанию `https://api64.ipify.org`, настраивается в профиле) в сравнении с ожидаемым,
доступность AI-провайдеров, GitHub и YouTrack — и показывает результат, причину ошибки и время. На самой машине
runner: `ai-runner test-network` (заодно показывает, доступен ли там Strict Egress и почему нет).

**Strict Egress** (Linux и WSL2): шаг с итоговым профилем `strict` выполняется только в песочнице на каждую попытку —
новых user-, network- и mount-namespace, которые runner создаёт без root. Внутри единственный интерфейс — собственный
loopback песочницы; nftables отклоняет всё остальное (IPv4, IPv6, DNS, UDP). Файловая система — минимальное
представление (KIN-80): системные каталоги (`/usr`, `/etc`, `/lib`, …) только для чтения, worktree и каталог попытки
доступны на запись, зеркало репозитория только для чтения (на запись — лишь index/HEAD своего worktree), приватный
`/tmp` и приватный `HOME` на попытку, где лежат только копии файлов авторизации CLI (`~/.claude/.credentials.json`,
`~/.claude.json`, `~/.claude/settings.json`, `~/.codex/auth.json`, `~/.codex/config.toml`; обратно ничего не
копируется, так что агент не может изменить логин или настройки последующих запусков). Из `/etc` видно только нужное
программам (пользователи, разрешение имён, корневые сертификаты TLS, часовой пояс, загрузчик). Настоящий `HOME` runner
(SSH-ключи, другие репозитории), его каталог данных (ключ Ed25519, другие попытки), `/opt`, `/run` (Docker, D-Bus, WSL
interop), `/mnt` (диски Windows) и всё остальное отсутствуют; CLI, установленный вне системных каталогов,
пробрасывается только для чтения. Единственный выход — локальный proxy adapter
runner, который применяет allowlist профиля и подключается через upstream-прокси (HTTP CONNECT, HTTPS-прокси или
SOCKS5 с remote DNS; учётные данные в песочницу не попадают). Перед запуском CLI внутри песочницы проходит preflight:
прокси доступен, внешний IP совпадает с ожидаемым, прямой TCP (IPv4/IPv6), DNS, клиент без `HTTP_PROXY` и сокеты
хоста заблокированы, `HOME` и каталог данных runner не видны, `/` и системные каталоги недоступны на запись. Иначе CLI не запускается, шаг ждёт (WAITING, причина `network`) и повторяется через две минуты,
а при повторах подряд на том же runner интервал удваивается (до 30 минут; с третьего раза Owner получает алерт egress
по этому runner); прямого fallback нет. Пока CLI работает, runner каждые 5 минут заново проверяет внешний IP: при
несовпадении (или двух неудачных проверках подряд) адаптер обрывает все соединения, и шаг так же ждёт сеть.
Соединения, отклонённые allowlist, подсчитываются и выводятся в конце вывода попытки. После перезапуска runner
подхваченная strict-попытка получает proxy adapter обратно на том же сокете либо останавливается и ждёт сеть. Runner сообщает `strictEgress` только после успешной самопроверки песочницы, и планировщик
отдаёт strict-шаги только таким runner (macOS — не поддерживается). Обход разрешений CLI
(`--dangerously-skip-permissions` и аналоги) допускается только внутри этой песочницы. Требования: установлен `nft` и
разрешены непривилегированные user namespaces (Ubuntu 24.04:
`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`). Ограничения: `git add`/`git commit` агента внутри песочницы не проходят (объекты
зеркала только для чтения; коммитит runner после запуска); логин CLI, обновлённый внутри песочницы, не сохраняется;
нужен Linux 5.12+. **Без песочницы** (macOS, нет user namespaces или профиль не `strict`) CLI
работает на хосте под uid runner с настоящим `HOME`: он может прочитать всё, что доступно пользователю runner (SSH-ключи,
ключ и каталог данных runner, другие репозитории). Поэтому обход разрешений там выключен и CLI спрашивает перед
действиями; для недоверенных задач используйте strict egress.

**Логины и сессии CLI на runner** (KIN-86). CLI работают с каталогом CLI: по умолчанию это `HOME` пользователя runner,
либо отдельный каталог — `ai-runner run --cli-home <dir>` (или `KINDEV_RUNNER_CLI_HOME`; вне каталога данных,
создаётся с правами 0700), чтобы логины runner не смешивались с вашими. Залогиньте CLI туда явно:

```bash
claude setup-token                          # на любой машине с браузером: печатает токен на один год
ai-runner cli-login claude --cli-home <dir> # вставьте его (скрытый ввод; или stdin, или --token-file <файл 0600>)
ai-runner cli-login codex --cli-home <dir> -- --with-api-key   # запускает `codex login` с HOME=<dir>
ai-runner cli-login status --cli-home <dir>                    # чем залогинен каждый CLI, срок токена
```

Токен Claude остаётся на хосте (`<dir>/.kindev/claude-oauth-token`, 0600) и передаётся Claude Code через
`CLAUDE_CODE_OAUTH_TOKEN`; обновлять его не нужно, поэтому в песочнице ничего не теряется, а в выводе попыток он
маскируется. Агент в песочнице может прочитать логин, с которым работает, но не может записать логин хоста: файлы
авторизации — копии. Короткоживущий интерактивный логин (`claude` → `/login`, ChatGPT-логин Codex) тоже работает, но
его обновление внутри песочницы теряется — лучше токен (для Codex — API-ключ). Попытка в песочнице, у CLI которой нет
логина (или токен истёк), завершается до старта CLI как разлогиненный CLI: шаг удерживается, Owner получает алерт
(`cli_limit`, причина `auth`); runner также предупреждает при старте и за месяц до истечения токена. Для `--resume`
между попытками у каждой задачи своё хранилище сессий в каталоге данных (`cli-sessions/<project>/<task>/<cli>`),
смонтированное в песочнице в `~/.claude/projects` / `~/.codex/sessions`: попытка видит только сессии своей задачи, но
не чужих задач и не ваши; хранилища, не использовавшиеся 30 дней, удаляются. Хранилище задачи ограничено 256 MiB и
20 000 записей (файлы, каталоги, symlink): перед попыткой удаляются самые старые файлы сессий, пока хранилище не
уложится в 3/4 обоих лимитов (вывод попытки об этом сообщает), а во время попытки runner измеряет хранилище каждые
2 секунды и останавливает попытку, превысившую любой из лимитов или чьё хранилище не удаётся измерить (она завершается
с причиной; превышение возможно на объём, записанный за эти секунды). На macOS strict-песочницы нет, поэтому нет и хранилища сессий с этим лимитом: CLI
хранит сессии в своём домашнем каталоге. Для Claude Code strict-профилю нужен
`api.anthropic.com` в allowlist (телеметрия на `*.datadoghq.com` — по желанию).

### Согласования и политика риска

Эффективный риск каждой ревизии плана считает детерминированный **Policy Evaluator**: правила проекта (пути,
миграции, auth/безопасность, схема БД — glob-шаблоны, `**` — любые папки) могут только повысить предложенный AI
уровень, но не понизить. Планы L0/L1 сразу переходят в READY и сливаются в dev по политике; планы L2/L3 ждут Owner на
странице **Согласования**, плюс отдельный запрос *слияние в dev*, который решается после проверки. Решение указывает
ревизию плана и её `planHash`; новая ревизия аннулирует ожидающие согласования, а одобрение старой возвращает 409.
Выполняемый шаг, изменивший файлы вне одобренного scope (или выше одобренного риска), останавливается, пока Owner не
одобрит дополнительные файлы. Решает и меняет политику только Owner; Project Admin видит согласования и политику своих
проектов. API: `GET /api/approvals?state=pending|decided|all`, `GET /api/approvals/{id}`,
`POST /api/approvals/{id}/{approve|reject}` (`planRevision`, `planHash`, `comment` — обязателен при отказе),
`GET/PUT /api/projects/{id}/risk-policy`.
Любая ревизия плана задачи с изменениями относительно предыдущей (добавленные, удалённые и изменённые шаги; scope,
риск, тесты, миграции) открывается на `/tasks/{id}/plan/revisions/{n}` всем, кто видит задачу
(`GET /api/tasks/{id}/revisions/{n}?base=m` сравнивает с ревизией `m`).
### Журнал аудита

Действия, важные для безопасности, пишутся в журнал аудита (только добавление) в той же транзакции, что и само
действие: завершение первичной настройки; вход, неудачный вход (адрес и причина; логин — только если такая учётная
запись существует, пароль — никогда; попытки, отклонённые ограничителем частоты, не пишутся) и выход; создание,
отключение и включение учётной записи, сброс и смена пароля; создание, отзыв и принятие приглашений; создание проекта,
назначение и снятие роли участника; создание и отзыв токенов регистрации раннеров, регистрация раннера (или отклонённая попытка с известным токеном), одобрение, смена проектов, отключение, включение и отзыв раннера (следующие контексты — approvals, интеграции — добавят свои события). Записи нельзя изменить или
удалить (это запрещают триггеры БД, и API для этого нет); значения, похожие на пароли и токены, сохраняются как
`[redacted]`. Owner читает журнал на странице **Аудит** или через
`GET /api/audit?actor=&project=&kind=&from=&to=&before=&limit=` (сначала новые, `next` — курсор следующей страницы);
остальным пользователям — `403`. Автоочистки в MVP нет.

### Резервное копирование, восстановление и перенос

Автоматических бэкапов в MVP нет; `export`/`import` переносят установку вручную. Control Plane — единственный
экземпляр: кроме lock-файла `data/ai-platform.lock` он держит в базе запись экземпляра (хост, pid, heartbeat), поэтому
второй процесс на тех же данных не стартует — даже через сетевую ФС. Перезапуск на том же хосте
забирает запись сразу; для другого хоста она истекает через 30 секунд после последнего heartbeat, а экземпляр,
потерявший запись, останавливается.

1. **Режим обслуживания** (Owner, пункт меню *Обслуживание*): новые шаги не выдаются, запущенные доработают, раннеры
   продолжают сверку, изменения в UI/API приостановлены для всех (работают вход, вебхуки и действия безопасности:
   отмена задачи, отзыв/отключение раннера, отключение пользователя, отклонение согласования). Баннер
   показывает причину и сколько шагов ещё выполняется. Дождитесь нуля.
2. **Экспорт** (работает при запущенном сервере; онлайн-снимок SQLite, согласованный):
   ```bash
   ai-platform export --data-dir ./data --out backup.tar.gz --key-out backup.key
   # Docker: docker compose exec cp ai-platform export --data-dir /data --out /data/backup.tar.gz --key-out /data/backup.key
   #         docker compose cp cp:/data/backup.tar.gz . && docker compose cp cp:/data/backup.key .
   ```
   Архив содержит манифест (формат, версия, схема, id установки, SHA-256 каждого файла), базу и `data/artifacts/`.
   **Ключа шифрования в архиве нет никогда.** Выбор явный: `--key-out` пишет ключ в отдельный файл 0600,
   `--without-key` не экспортирует его, и вы копируете файл ключа сами. Владелец архива и ключа может прочитать все
   сохранённые секреты — передавайте их разными каналами и удаляйте лишние копии.
3. **Остановите старый Control Plane** (`docker compose down`), чтобы два экземпляра не работали одновременно.
4. **Импорт** в пустой каталог данных на новом хосте:
   ```bash
   ai-platform import --data-dir ./data --archive backup.tar.gz --key backup.key
   # Docker (файлы должны читаться uid 65532):
   # docker compose run --rm --no-deps -v "$PWD:/backup:ro" cp import --data-dir /data --archive /backup/backup.tar.gz --key /backup/backup.key
   ```
   Импорт проверяет манифест, все контрольные суммы, целостность базы, версию схемы (база от более нового бинаря
   отклоняется до любой записи) и соответствие ключа базе. Без ключа он останавливается с ошибкой — новый ключ не
   генерируется. Затем применяются недостающие миграции.
5. **Запустите** новый Control Plane, направьте на него DNS/`--public-url` и выключите режим обслуживания. Раннеры
   переподключатся сами; каждый запуск Control Plane использует новую эпоху канала команд, поэтому восстановленная
   (более старая) база не заставит раннер пропустить новые команды.

## Установка

Пошаговое развёртывание. Подробности по каждой части — в разделах выше.

### 1. Выберите профиль поставки

| Профиль | Команда | Для чего |
|---|---|---|
| Compose + HTTPS (Caddy) | `DOMAIN=ai.example.com docker compose --profile https up -d` | **Сервер.** Единственный публичный профиль в MVP. |
| Compose, обычный HTTP | `docker compose up -d` | Только эта машина: `http://127.0.0.1:8080`. |
| Standalone, обычный HTTP | `ai-platform serve` | Только эта машина, без Docker. |
| Standalone HTTPS (встроенный TLS/ACME) | — | Не входит в MVP. Используйте профиль Compose HTTPS. |

Для публичного доступа, Telegram Mini App и **удалённых runners нужен HTTPS**. Обычный HTTP (и `ws://` для runners)
подходит только для браузера и runner на том же хосте. Не публикуйте порт обычного HTTP: Compose привязывает его
к `127.0.0.1`.

**Хост Control Plane:** достаточно Linux VPS с 1 vCPU и 1 ГБ RAM. Нужны Docker с Compose v2, DNS-имя, указывающее
на хост, и открытые порты 80/443 для сертификата ACME. Не запускайте там runners, AI CLI и другие тяжёлые сервисы:
агенты работают на runners. Замер под `--cpus=1 --memory=1g` (KIN-42): 8 runners выполнили 1000 mock-задач за 33 с,
Control Plane занял не больше 50 МиБ RAM и 67% vCPU (около 11 МиБ в простое). Mock-задачи не проходили путь pull
request, CI и merge и не писали в YouTrack (нет GitHub App); это добавляет несколько вызовов outbox на задачу.
Настоящая AI-задача идёт минуты, поэтому нагрузка гораздо ниже. Повторить замер можно через `scripts/measure-cp.sh`.

### 2. Запустите Control Plane

```bash
git clone --branch vX.Y.Z https://github.com/tr1gl1de/kindevai.git && cd kindevai   # релиз: compose.yml ему соответствует
export KINDEV_IMAGE_TAG=X.Y.Z                       # тот же релиз
export DOMAIN=ai.example.com KINDEV_PUBLIC_URL=https://ai.example.com
docker compose --profile https pull && docker compose --profile https up -d
docker compose exec cp ai-platform setup-token     # одноразовый токен настройки, действует 1 ч
```

Откройте `https://ai.example.com`, введите токен и создайте Owner (пароль от 12 символов). `KINDEV_PUBLIC_URL`
закрепляет origin, к которому подключаются runners, и используется в ссылках комментариев YouTrack. Сохраните обе
переменные в профиле shell или в unit systemd: каждой следующей команде `docker compose` нужны те же значения.
Сразу сделайте копию ключа шифрования. Он создаётся при первом запуске, и без него ничего не расшифровать (шаг 9).

### 3. Защитите `main`/`master` на GitHub (обязательно)

> **Обязательно в любой установке.** В каждом репозитории, с которым работает платформа, ruleset или branch
> protection GitHub должны запрещать прямой push в `main`/`master` и merge в них. Обходить их можете только вы.

Почему платформа не справится с этим сама:

- Runner получает короткоживущий installation token GitHub App с правом **Contents: write** на репозиторий, в котором
  работает. GitHub ограничивает такой токен репозиторием, а не веткой, поэтому runner или агент, у которого токен
  утёк, может сделать push в любую ветку, включая `main`.
- Merge API GitHub (`PUT /repos/{owner}/{repo}/pulls/{n}/merge`) принимает только номер pull request и не фиксирует
  базовую ветку. Если между проверкой платформы и merge кто-то перенаправит pull request на `main`, merge попадёт
  в `main`.
- Платформа отказывает в коде любой записи в `main`/`master` (main/master guard; integration branch никогда не бывает
  `main`/`master`), runner тоже не делает туда push. Эти проверки защищают запросы самой платформы, но утёкший
  токен может остановить только GitHub.

Настройка каждого репозитория (**Settings → Rules → Rulesets → New branch ruleset**):

1. Целевые ветки: `main` и `master` (добавьте «Include default branch», если ветка по умолчанию — одна из них).
   Enforcement status: **Active**.
2. Правила: **Restrict updates**, **Restrict deletions**, **Block force pushes** и **Require a pull request before
   merging**.
3. Bypass list: только вы (или роль администратора репозитория). **GitHub App туда не добавляйте никогда.** С
   «Restrict updates» любое изменение ветки, включая merge pull request, доступно только вам.
4. Если вы выпускаете релизы из репозитория, добавьте ruleset тегов `v*`, где создавать, менять и удалять теги можете
   только вы, и environment `production`, где вы — обязательный reviewer.

На тарифе без rulesets то же делает классическая branch protection для `main`/`master` (обязательный pull request,
push только для вас, без обхода). После **Refresh** на странице Integrations у репозитория не должно остаться
предупреждения «main/master не защищены».

### 4. Подключите GitHub (GitHub App)

1. **GitHub → Settings → Developer settings → GitHub Apps → New GitHub App**:
   - webhook URL `https://ai.example.com/api/webhooks/github`, случайный webhook secret от 16 символов;
   - только права из раздела [GitHub App](#github-app) (Contents и Pull requests на чтение и запись, Checks и
     Metadata на чтение; **без** Administration и Workflows);
   - события Push, Pull request, Check suite и Check run.
2. Создайте private key (`.pem`) и установите App **только на репозитории**, с которыми работает платформа.
3. Страница **Integrations**: введите App ID, private key и webhook secret.
4. В каждом проекте зарегистрируйте репозитории как `owner/name`. Integration branch — `dev`, она должна
   существовать и никогда не бывает `main`/`master`. Укажите тестовую команду (например, `make test`). В репозитории
   нужен CI, который публикует **check runs** на pull requests (GitHub Actions публикует; устаревшие commit statuses
   не читаются). Без CI ничего не мержится: через 30 минут задача становится BLOCKED (причина `ci`).

### 5. Подключите YouTrack

1. Создайте для платформы отдельного пользователя YouTrack и постоянный токен для него. Пользователю нужно читать
   задачи и статьи Knowledge Base, комментировать, применять команды (смена состояния) и, если нужна запись в KB,
   изменять статьи.
2. Страница **Integrations**: введите базовый URL YouTrack и токен, затем **Test connection**.
3. В каждом проекте свяжите проект YouTrack по short name и выберите тег запуска (`kindevai`). Сопоставьте
   пользователей платформы с их логинами YouTrack: задачу запускает только учётная запись того, кто поставил тег.
   При желании сопоставьте состояния задач с состояниями YouTrack
   (`PUT /api/projects/{id}/integrations/youtrack/states`) и настройте webhook. Polling работает и без него.

### 6. Telegram (необязательно)

1. Создайте бота через [@BotFather](https://t.me/BotFather) (`/newbot`) и сохраните его токен.
2. Создайте Mini App командой `/newapp` с HTTPS-адресом сайта, `https://ai.example.com/`. Telegram принимает
   только HTTPS.
3. **Settings → Telegram** (`/settings/telegram`, Owner): введите username бота, short name Mini App и токен бота.
   Токен хранится зашифрованным.
4. Каждый пользователь сам привязывает свой Telegram на странице **Account** (одноразовая ссылка и 6-значный код).
   Алерты приходят привязанным пользователям в Telegram.

### 7. Добавьте runner

**Хост runner:** Linux x86_64/aarch64, WSL2 с systemd или macOS arm64/x86_64. Нужны `git` и AI CLI (`claude`, `codex`)
в PATH и минимум 2 ГиБ свободного места на каждый workspace. **Strict egress** (песочница, без которой CLI не получает
обход разрешений) работает только на Linux/WSL2 и требует ядро 5.12+, `nft` и непривилегированные user namespaces.
Ubuntu 24.04 их ограничивает, поэтому разрешите их постоянно:

```bash
echo 'kernel.apparmor_restrict_unprivileged_userns=0' | sudo tee /etc/sysctl.d/60-kindevai-userns.conf
sudo sysctl --system
```

1. Скачайте `kindevai-runner_<version>_<os>_<arch>.tar.gz` и `SHA256SUMS` из одного GitHub Release, проверьте и
   установите:
   ```bash
   sha256sum --check --ignore-missing SHA256SUMS
   tar -xzf kindevai-runner_*_linux_amd64.tar.gz ai-runner && sudo install -m 0755 ai-runner /usr/local/bin/
   ```
2. **Runners → Add runner** показывает одноразовый токен (действует 10 минут). Зарегистрируйте runner командами из
   начала `deploy/runner/kindevai-runner.service` (systemd, отдельный пользователь), `kindevai-runner-user.service`
   (WSL2 или ваш пользователь) или `io.kindevai.runner.plist` (macOS). Токен читается из скрытого ввода или файла
   0600, никогда из командной строки.
3. Сравните `ai-runner fingerprint` с карточкой runner и одобрите его для нужных проектов.
4. Залогиньте CLI там, где работает runner, от пользователя runner. Учётные данные остаются на этом хосте:
   ```bash
   claude setup-token                               # на любой машине с браузером
   ai-runner cli-login claude                       # вставьте токен (скрытый ввод)
   ai-runner cli-login codex -- --with-api-key      # Codex: API-ключ
   ai-runner cli-login status
   ```
5. `ai-runner test-network` проверяет выход в сеть и доступность strict egress. Запускайте сервис с
   `ai-runner run --measure-space`, если страница Storage должна показывать, что занимает место на runner.

Удалённые runners подключаются только по `wss://` (профиль HTTPS). Машина WSL2 или ноутбук, который засыпает, — это
нормально: их попытки становятся `UNKNOWN` и сверяются, когда машина вернётся. Обновляйте Control Plane и runners
вместе, до одного релиза.

### 8. Сетевые профили и прокси (необязательно)

Страница **Network** (Owner): создайте профиль с upstream-прокси, ожидаемым выходным IP и allowlist и назначьте его
установке, runner, проекту или CLI. Профиль `strict` запускает CLI в песочнице, которая через прокси достаёт только
до allowlist. Для Claude Code там нужен `api.anthropic.com`, плюс ваши хосты GitHub и YouTrack. **Test Network**
проверяет профиль с runner, прежде чем на него полагаться.

### 9. Резервные копии и обновления

Автоматических резервных копий в MVP нет. Один раз скопируйте ключ шифрования и храните его отдельно от архивов
(он не меняется), затем регулярно делайте export. Export работает, пока Control Plane обслуживает запросы:

```bash
docker compose cp cp:/data/secrets/master.key ./kindevai-master.key && chmod 600 ./kindevai-master.key  # один раз
f=backup-$(date +%F).tar.gz
docker compose exec cp ai-platform export --data-dir /data --out /data/$f --without-key
docker compose cp cp:/data/$f .
docker run --rm -v kindevai_data:/data busybox rm /data/$f   # в образе нет shell: удалите копию из volume
```

Для переноса или восстановления следуйте разделу
[Резервное копирование, восстановление и перенос](#резервное-копирование-восстановление-и-перенос) и никогда не
запускайте два Control Plane на одних данных. Для обновления сначала сделайте export, затем задайте новый
`KINDEV_IMAGE_TAG` и выполните `docker compose --profile https pull && docker compose --profile https up -d`.
Миграции применяются при запуске. Затем обновите runners.

### Чек-лист

- [ ] Профиль Compose HTTPS с настоящим `DOMAIN`, задан `KINDEV_PUBLIC_URL`, порт обычного HTTP не публичный.
- [ ] Ключ шифрования скопирован и хранится отдельно от резервных копий.
- [ ] **Rulesets или branch protection на `main`/`master` в каждом репозитории**, обход только у вас, App в списке
      нет. Страница Integrations не показывает предупреждения о защите.
- [ ] GitHub App с минимальными правами, установлен только на репозитории платформы. Ветка `dev` есть, CI запускается
      на pull requests.
- [ ] Пользователь интеграции YouTrack с постоянным токеном, проекты связаны, пользователи сопоставлены.
- [ ] Runners проверены по fingerprint, одобрены для конкретных проектов, CLI залогинены, `ai-runner test-network`
      проходит.
- [ ] Регулярный `ai-platform export`.

## Docker Compose

```bash
docker compose up -d                                        # один контейнер, http://127.0.0.1:8080
DOMAIN=ai.example.com docker compose --profile https up -d  # + Caddy с автоматическим HTTPS на 80/443
docker compose exec cp ai-platform setup-token        # setup token для первой настройки
```

`.env` не нужен. HTTP-порт публикуется только на loopback хоста; публичный доступ — через профиль `https`
(DNS для `DOMAIN` должен указывать на хост). Данные и ключ шифрования лежат в volume `data` — сохраняйте его
целиком. Образ distroless, работает от непривилегированного пользователя с read-only корневой ФС и встроенной
проверкой здоровья (`ai-platform health`).
За Caddy ограничения частоты по клиенту используют `X-Forwarded-For` только от сети compose
(`KINDEV_TRUSTED_PROXIES`, по умолчанию `172.29.240.0/24`; при конфликте задайте `KINDEV_SUBNET`). Базовые образы
закреплены по digest. Без `DOMAIN` профиль https отдаёт `https://localhost` с внутренним CA Caddy.

## Разработка

```bash
make help             # список целей
make dev              # запустить Control Plane на порту этого worktree
npm --prefix web run dev   # Vite dev server, проксирует /api в Control Plane
make test             # Go-тесты (-race -shuffle=on) + unit-тесты web + тесты хуков/скриптов
make lint             # go vet + проверка типов TypeScript
make clean            # удалить артефакты сборки и тестов
```

Ветки создаются от `dev` как `feature/KIN-<n>-<slug>`; pull request — только в `dev`. `main` — только для владельца.

## CI и релизы

| Событие | Что выполняется |
|---|---|
| PR или push в `dev` / `main` | `make lint` (go vet, golangci-lint, oxlint, tsc), тесты с покрытием, `make vuln` (govulncheck, npm audit), `make build`, проверка конфига GoReleaser, actionlint, сборка Docker-образа и смоук-тест |
| Зелёный push в `dev` | **Dev-сборка**: бинарники Control Plane и раннера linux/darwin × amd64/arm64 + `SHA256SUMS` как артефакт прогона CI `ai-platform-dev-<sha>` (хранится 14 дней); образ `ghcr.io/tr1gl1de/kindevai-dev:latest` (отдельный dev-пакет) |
| Тег `v*` на коммите `main` (только владелец) | **Prod-релиз**: проверка, что тег на `main`, тесты, GitHub Release (changelog, checksums, provenance) и образ `:X.Y.Z`, `:X.Y`, `:latest` через защищённый environment `production` |

Автоматизация никогда не пушит в `main` и не создаёт PR в `main`. Dependabot еженедельно предлагает обновления в `dev`.
Все сторонние actions и образы закреплены по SHA/digest.

**Обязательные настройки репозитория (владелец, один раз)** — workflow сами их обеспечить не могут:
1. Rulesets: защитить `main` (push/merge только владелец) и теги `v*` (создавать, менять, удалять — только владелец).
2. Environment `production`: обязательный ревьюер — владелец, без обхода администраторами, deployment tags `v*`.
3. Пакет `ghcr.io/tr1gl1de/kindevai`: права записи из Actions только для этого репозитория (dev-образы — в
   `kindevai-dev`).
Локально: `make lint vuln build`, `make release-snapshot` (нужен GoReleaser).
